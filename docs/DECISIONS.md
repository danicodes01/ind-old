# IND — Architecture Decision Record

Every significant technical choice, why it was made, and what it commits us to. Append new
entries at the end; never rewrite history. If a decision is reversed, add a new ADR that
supersedes the old one and mark the old one accordingly.

All entries below were made during the foundation stage, before implementation.

---

## ADR-001 — Expo SDK 57

**Decision.** Expo SDK 57 (React Native 0.86, React 19.2, New Architecture), managed workflow
with development builds. TypeScript strict, React Compiler enabled, expo-router v6 with typed
routes.

**Why.** SDK 57 is current stable and shipped explicitly as a non-breaking upgrade over 56,
which makes it a low-risk foundation. The managed workflow with custom dev builds gives native
module access without owning the `ios/` and `android/` directories, and EAS handles the build
and submission pipeline that a solo project would otherwise have to maintain.

**Consequences.** Expo Go is not usable once native modules are added — development requires a
custom dev build. SDK upgrades are an annual-ish cadence to keep pace with.

---

## ADR-002 — Local-first: SQLite is the source of truth

**Decision.** The on-device SQLite database is authoritative. All reads and writes go to it
directly and synchronously. The server holds a replica, reconciled in the background.

**Why.** Offline is IND's normal case, not an edge case — shifts get logged in basements, walk-
ins, and car parks. A server-authoritative design would put latency and loading states in front
of the interaction that most needs to feel instant, and would make the app useless exactly when
people reach for it. It would also put every user's income data on a server as a precondition of
the app working at all.

**Consequences.** We must write and maintain a sync protocol ([SYNC.md](SYNC.md)). Accepted,
because IND's data shape — single-writer, small rows, append-mostly, no collaborative editing —
is the easiest case sync has.

## ADR-003 — Drizzle ORM with generated migrations

**Decision.** Drizzle ORM over `expo-sqlite`, with migrations generated by `drizzle-kit`,
committed to the repository, and applied at app start. Reactive reads via `useLiveQuery`.

**Why.** An app that records years of financial history cannot ship without a real, versioned,
forward-only migration story — that is the single most production-critical property of the data
layer, above ergonomics. Drizzle provides typed schema and generated SQL migrations, and its
`useLiveQuery` gives reactive reads without a caching layer.

**Consequences.** Migrations are committed artifacts and never edited after release. Every
migration gets a test that seeds the prior schema, migrates, and asserts data survived.

## ADR-004 — Accounts are free; Pro is cloud backup and sync

**Decision.** Anyone can create an account at no cost. Pro enables automatic cloud
backup/restore and multi-device, cross-platform sync. Free users get unlimited local use and
unrestricted export of all their data, forever. No account is required to use the app.

**Why.** Separating identity from entitlement keeps upgrade friction at one tap and avoids
building a second identity path later. Unrestricted free export is what keeps charging for sync
fair rather than coercive — we sell automation, not access to someone's own records. And no
sign-up wall, because utility apps lose most of their users at a login screen.

**Consequences.** A free signed-in account is an identity that syncs nothing, which is an easy
thing for UI to misrepresent — it must never imply backup. The most compelling paid feature is
now sync, so other Pro value (insights, reports, tax exports) is an open product question.

---

## ADR-005 — Durability is the product, so the server is committed

**Decision.** A backend is a planned, committed part of the architecture, not a hedge. The sync
path is designed from migration 001 rather than retrofitted.

**Why.** Recorded verbatim, because it is the reasoning that drove the decision:

> For a financial tracker, "never lose your records" and "it's on my iPad too" is probably the
> most compelling thing you could charge for. More compelling than extra charts. If that's what
> you sell, then yes — the server is coming, and it's a scheduled milestone, not a maybe.

Losing years of someone's income records because they dropped their phone is a product failure
whether or not they ever paid. OS-level backup (iCloud, Android Auto Backup) covers some of this
incidentally, but fails exactly where it hurts — full iCloud storage, cross-platform moves,
stale snapshots — so it cannot be relied on.

**Consequences.** Sync-readiness is a hard requirement of the initial schema: UUIDv7 ids,
server-assigned `updated_at`, soft deletes, per-row pending state. These cost little now and
would be a risky migration later.

## ADR-006 — Sync: per-row last-write-wins, with optimistic concurrency and nothing discarded

**Decision.** Per-row LWW ordered by server-assigned `updated_at`. Pushes carry a
`base_updated_at` for optimistic concurrency. Any version that loses a conflict is preserved in
a local `sync_conflicts` table rather than discarded. Keyset pagination on `(updated_at, id)`.
Full specification in [SYNC.md](SYNC.md).

**Why.** LWW is genuinely correct for single-writer data rather than a shortcut — but only if
nothing is silently destroyed. Optimistic concurrency is what makes a clobber _detectable_,
which is what allows the losing version to be kept. CRDTs and operational transforms would be
substantial complexity for a problem this data shape doesn't have.

**Consequences.** One extra field on the wire and one extra local table. Device clocks are never
trusted for ordering — `updated_at` is always assigned by Postgres. Soft-deleted rows purge
after 90 days, which obliges any device offline longer than that to perform a full resync rather
than sync incrementally.

**Amended during foundation review — the asymmetric delete rule is withdrawn.** The original
draft specified that a local edit beats a remote delete while a local delete beats a remote
edit. Walking the two-device delete/edit conflict in both sync orders showed the protocol never
consults such a rule: the optimistic-concurrency base check decides the outcome before any
delete-versus-edit reasoning applies, and the pull-side "keep local" step only defers the
decision. The rule described an intent the mechanism did not implement.

The operative rule is simply **first writer to reach the server wins; the second adopts the
server version and its own is preserved in `sync_conflicts`**. Both orderings were walked and
converge — see [SYNC.md](SYNC.md#convergence), where the proof is recorded and is a required
test case. Implementing the asymmetry for real would need a re-push-as-undelete round trip and
would let a stale edit on a forgotten device silently revive a deliberately deleted record.
Since neither version is destroyed either way, the simpler rule wins.

## ADR-007 — Money as integer minor units

**Decision.** All monetary values are `{ amount_minor: integer, currency: ISO-4217 }`. No
floating point anywhere in storage, arithmetic, or transport. The minor-unit exponent is a
per-currency property, never a hardcoded 100. Division uses largest-remainder allocation with a
guarantee that parts sum exactly to the original. Aggregation never crosses currencies.

**Why.** `0.1 + 0.2 !== 0.3`, and that error compounds across a year of shift totals. These
numbers may end up on a tax return. Tip pooling and tip-outs make division routine, and naive
division loses or invents cents. Not every currency has two decimal places.

**Consequences.** `domain/money` is the only representation of money in the codebase; a bare
`number` amount is a bug. Mixed-currency periods display separate totals rather than one wrong
number, until there is a product answer for exchange rates.

## ADR-008 — Time: instants, business date, and IANA zone stored separately

**Decision.** Every shift stores `started_at` and `ended_at` as epoch-ms UTC instants, a
`work_date` business day, and an IANA `tz`. Durations are computed from instants only; wall-clock
values are for display only, resolved through `tz`. Week starts and pay periods are per-job
configuration.

**Why.** None of the four is derivable from the others. "Which day's shift is this" is a human
judgement — a bartender clocking out at 3am means the previous night — and deriving it from
either timestamp breaks for overnight or split shifts. Timezone must be per-shift because people
travel; the zone rather than the offset, because offsets change and zones don't. And a shift
across the spring-forward boundary is seven hours, not eight — people get paid for elapsed time.

**Consequences.** `domain/time` is the only place duration arithmetic is written. Computing a
duration by subtracting local times is a bug. Overtime and pay-period logic reads its boundaries
from the job, never from the locale.

## ADR-009 — Single repository, one app, no admin application

**Decision.** One repository, one package, no workspaces. No separate admin or web application.

**Why.** A single-user tracker has no users or content to administer. Support and revenue
tooling, if ever needed, is covered by Supabase Studio, App Store Connect, and the payment
provider's dashboard for a long time. npm workspaces plus Metro monorepo resolution plus EAS
workspace builds is a permanent tax that buys nothing until a second app exists.

**Consequences.** `domain/` is kept free of React, React Native, and I/O imports (see
[ADR-015](#adr-015)), so promoting it to a shared package is mechanical if a second surface ever
appears. Revisit only if a real back-office need materialises.

## ADR-010 — Supabase as the backend, behind a port

**Decision.** Supabase provides Postgres, Auth (Apple, Google, email magic link), and row-level
security. It is reached exclusively through two interfaces — `AuthPort` and `SyncTransport` —
and `@supabase/supabase-js` may only be imported inside
`src/data/sync/adapters/supabase/**`, enforced by ESLint.

**Why.** Sign in with Apple, Google sign-in, refresh-token rotation, and RLS are a large amount
of undifferentiated work, and none of it is IND's actual problem. But the choice is reversible
in principle and should stay reversible in practice, so it sits behind a boundary. The port is
narrow enough — two interfaces, six methods — that the indirection is nearly free.

**Consequences.** No Supabase type crosses the port; `Session` is ours. Postgres errors are
translated into our own `SyncError` taxonomy at the adapter edge. A `FakeTransport` implementing
the same interface makes the protocol testable with no network. Replacing Supabase means writing
one adapter directory and changing nothing else.

## ADR-011 — In-app purchase implementation deferred

**Decision.** No purchase SDK is installed during the foundation stage. The decision between
StoreKit 2 via `expo-iap`/`react-native-iap` and RevenueCat is deferred until there are products
to sell.

**Why.** StoreKit 2 verifies transactions cryptographically on-device with no server, so a
purchase SDK does not require a backend — the "you need RevenueCat or a server" framing is out
of date. RevenueCat's value is the subscription edge cases (grace periods, billing retry,
proration, refunds, cross-platform entitlement) and it costs roughly 1% of tracked revenue above
a free threshold. Installing either now would mean a dependency pointed at nothing.

**Consequences.** Entitlement is read through a single call site so that either implementation
drops in without touching feature code. Android's local verification is weaker than iOS's; if
piracy becomes a real concern, server-side validation is the answer. Current RevenueCat pricing
should be re-checked before deciding.

## ADR-012 — Telemetry: crash and error reporting only

**Decision.** Crash and error reporting only, with all monetary values and PII scrubbed. No
product analytics. Reporting sits behind an interface in `lib/telemetry` so the provider is
swappable and can be a no-op. **Confirmed during foundation review.**

**Why.** Shipping blind to crashes is untenable for a paid app, but an app holding people's
income records should collect as little as possible. Until sync ships, this keeps the App Store
privacy label at "Data Not Collected", which is a genuine asset for this product.

**Consequences.** Less product insight than analytics would give; accepted deliberately. Scrubbing
is not best-effort — monetary values and PII must be stripped before a report leaves the device,
and that is a tested property of `lib/telemetry`, not a configuration setting. If conversion
analytics are ever justified by monetization, that is a new ADR superseding this one, not a
quiet loosening of it.

## ADR-013 — Theming: typed semantic tokens over `PlatformColor`

**Decision.** A typed semantic token layer resolving to Apple `PlatformColor` /
`DynamicColorIOS` on iOS and to HIG-equivalent hex values on Android.

**Why.** The app should feel like it belongs to the OS rather than like a cross-platform shell.
Binding to real system semantic colors means light/dark, increased contrast, and future OS
palette changes are handled natively with no abstraction tax. A thin typed layer keeps Android
consistent without a styling framework between us and those colors.

**Consequences.** No NativeWind, Tamagui, or Unistyles. Token names are semantic (`textPrimary`,
`surfaceElevated`), never literal colors, so the palette can change centrally.

---

## ADR-014 — No server-state library

**Decision.** No TanStack Query or equivalent. Reads go through repositories to Drizzle
`useLiveQuery` against local SQLite.

**Why.** There is no server in the read path. A server-state cache would be ceremony wrapped
around a local database that is already reactive, and would introduce cache invalidation as a
problem we don't otherwise have.

**Consequences.** Revisit only if a genuinely remote read path appears — remote-only reports,
say. Background sync is not that: it writes to the local database, and live queries pick the
changes up for free.

---

## ADR-015 — `domain/` purity is enforced by lint

**Decision.** `src/domain/**` may not import from `react`, `react-native`, `expo-*`,
`drizzle-orm`, `@supabase/*`, or any other application layer. Enforced by ESLint
`no-restricted-imports`, not convention.

**Why.** The riskiest logic in IND — money arithmetic, DST-safe durations, pay rules — should
run as fast unit tests with no simulator, no database, and no mocking. That is the difference
between a test suite that gets run and one that doesn't. It also keeps `domain/` liftable into a
shared package without untangling, which is what makes [ADR-009](#adr-009) safe.

**Consequences.** Domain code takes primitives and returns values; anything needing I/O lives in
`data/`. Enforced mechanically, so it cannot erode quietly.

## ADR-016 — Local rows carry no user identity

**Decision.** `user_id` exists in Postgres, where RLS depends on it, and in no SQLite table.
Account identity is held once in a singleton `local_account` table, read only by the sync
engine.

**Why.** An installation holds exactly one account's data, so a per-row owner would be the same
value on every row — carrying no information, meaningless while anonymous, and requiring a mass
`UPDATE` across the whole database at sign-in. It would also embed Supabase's notion of identity
into the middle of the financial model, which is the coupling [ADR-010](#adr-010)'s port
boundary exists to prevent. Decisively: the server derives `user_id` from the verified JWT and
rejects it from the client payload, so the column is not merely redundant on the device, it is
unused on the wire.

**Consequences.** Domain rows are financial records and nothing else — they carry no trace of
how the user authenticated, and `domain/` needs no concept of an account. Linking an account is
a single-row write. The cross-account guard that a per-row owner would have provided is instead
enforced by the sync engine comparing the signed-in account against `local_account` and refusing
to sync on mismatch. Supporting multiple accounts on one installation would need revisiting
this, and is explicitly not supported.

## ADR-017 — Replication state is an enum, not a dirty flag

**Decision.** Each local row carries `_sync_state` of `local_only`, `synced`, or `modified`,
plus `_base_updated_at` which is non-null exactly when the row has been replicated. This
replaces a boolean `_pending`.

**Why.** A boolean conflates two independent facts: whether a row has _ever_ been replicated,
and whether it has changed _since_ it was. For a free user the distinction is the whole point —
their rows are not pending anything. Nothing is queued, retrying, or stuck; those records live
on one device, which is the product working as designed. Describing that as "pending" for years
would misdescribe the system to anyone reading the schema and would make any "changes waiting to
sync" figure meaningless.

**Consequences.** `local_only` already means "needs upload," so enabling sync requires no pass
over the data to mark anything — the push set is already correct. Together with
[ADR-016](#adr-016) this makes signing in an O(1) metadata write rather than an O(n) rewrite of
every row, and removes the resumable-adoption problem the earlier design had to solve. Pull
reconciliation keys off `_sync_state != 'synced'` rather than a pending bit.
